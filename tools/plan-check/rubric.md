# Rubric: is this plan ready to post and build from?

Grade the proposed work against the reproduced behavior, not the length, headings, or confidence of the draft. In eval mode the frozen package is the only evidence. In live mode use the scoped issue, the student's posted reproduction quoted or linked in the drafts, and the repository's contributor guidance.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Evidence-grounded diagnosis | Issue behavior; Repro evidence steps, actual and expected output, and controls; Candidate plan cause and Candidate plan comment causal claims. Live: the same facts quoted from the student's posted repro and issue thread. | The proposed mechanism explains the reproduced trigger and result without contradicting a shown control, environment constraint, or artifact. Observations and hypotheses are distinguished. A testable hypothesis can pass when the approach first checks it against the reproduced behavior; repeating a thread theory that the reproduction rules out fails. | required |
| Cause-directed change | Candidate plan's proposed operation read against its diagnosis, the issue's expected behavior, and the reproduction's controls; live plan and quoted repro equivalents. | The change addresses the mechanism responsible for the observed result and preserves the requested behavior. Merely hiding the symptom, swallowing unrelated errors, weakening a test to match incorrect behavior, or repairing a neighboring problem fails. A workaround can pass only if its limitation is explicit and it satisfies the issue's requested outcome and stated maintainer constraints. | required |
| Bounded scope | Issue goal and maintainer direction; Candidate plan in-scope and out-of-scope statements, affected files/areas, and approach; Candidate plan comment commitments. | The work serves one issue outcome and identifies the affected area and boundaries. Related helpers, tests, and documentation may belong to that outcome. Unrelated refactors, redesigns, platform expansion, new features, or semantic changes beyond the agreed goal fail. A stated narrow slice is sufficient only if its proposed operations actually stay within that slice. | required |
| Executable approach | Candidate plan's files/functions/areas, operations, work order, dependencies, and unresolved questions; live draft equivalents. | A contributor can start from a named code area and a specific proposed operation, then reach the intended change without inventing the implementation direction. Exact line numbers and a fixed number of steps are not required. A necessary private fixture, unspecified algorithm, or "investigate and fix it" with no starting mechanism or concrete next action holds the package. | required |
| Decisive verification | Repro evidence's trigger, environment, artifacts, and controls compared with Candidate plan's test plan and Candidate plan comment validation promise. | The plan reuses or explicitly references the reproduced trigger and relevant conditions, names the observable expected result after the fix, and identifies how that result will be checked through the affected behavior. A precise reference to the supplied repro steps is enough. Performance checks compare the same workload and relevant options; UI checks name the visible behavior. "Run the suite", "nothing regresses", or "it works" alone do not prove the issue is fixed. | required |
| Honest uncertainty | Candidate plan diagnosis, risks, unknowns, assumptions, and deviations; Candidate plan comment claims read against issue and Repro evidence. | Claims stay within the supplied evidence. A material unknown is stated as an unknown with a bounded way to check it before relying on it, and a discovered deviation says what changed and why. A terse plan need not invent a risk when none is evidenced. Unsupported certainty, an untested root-cause assertion contradicted by the artifacts, or hiding a known behavior change fails. | required |
| Thread and conventions | Thread highlights and Repo facts contribution policy/template asks; Candidate plan comment compared with Candidate plan and repro. Live: the full issue thread, contributor docs and linked policies, draft comment, and voice guide. | The comment presents this contributor's diagnosis, proposed change, and validation, agrees with the plan and repro, and follows explicit maintainer direction and posting conditions. Include AI disclosure when required and respect a stated human-authored-comment rule; claiming compliance does not excuse text that explicitly contradicts it. Silence creates no extra policy requirement. Do not substitute a generic pledge or another person's plan. In Path Review, another student's claim or plan does not block this student's independent plan. | required |
| Regression coverage | Candidate plan's controls or neighboring cases compared with the shared code path and issue-specific risks in Repro evidence. | A relevant control, unaffected neighboring behavior, or shared-path regression check is named in addition to the decisive reproduction check. | preferred |

## Verdict rule

Return `accept` (ready) only if every required check is `pass`. Return `reject` (hold) if any required check is `fail` or `unclear` after gathering its named evidence. Grade every check even after a deciding failure. Preferred grades never change the verdict. Use `unclear` only when the needed evidence is genuinely absent or cannot be verified after looking; use `fail` for an observed contradiction or unmet condition. Report the deciding fact for every check and end with the skill's fenced JSON object.
